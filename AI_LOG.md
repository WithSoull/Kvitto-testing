# AI_LOG

## Инструменты
- Claude Code (десктоп), модель Claude Opus 5.5 — спека, архитектура, код, тесты.
- Отдельный субагент Claude без контекста переписки — независимое ревью.
- Правила для агентов — [CLAUDE.md](CLAUDE.md), решения — [docs/DECISIONS.md](docs/DECISIONS.md).

## Ключевые запросы
1. **Сначала спека, код потом.** Контекст: ТЗ (PDF) и стек.
   > «Для начала мы сформируем четкую спеку с ТЗ и спроектируем архитектуру. Стек: Python,
   > FastAPI, Postgres, Alembic, Docker, OpenAPI 3+. Также нужно составить базовый CLAUDE.md, в
   > котором будут описаны правила для исполняющих агентов. Задавай уточняющие вопросы как по
   > архитектуре, так и по организации окружения, так и по правилам написания кода»

   Получил 4 раунда вопросов. По каждому спорному месту ТЗ решение принимал я: например, тот
   же `Idempotency-Key` с другим телом → 422.
2. **Варианты разбирал с моделью, решения оставлял за собой.** Контекст: вопросы модели по
   архитектуре.
   > «Давай это обсудим: оба ли варианта нам доступны и в какой момент после MVP нам нужно будет
   > прибегнуть к async»

   > «все такие подводные камни мы должны собирать в отдельную заметку» → docs/DECISIONS.md
3. **Ревью в два независимых прохода.** Контекст: готовый PR.
   > «проведи ревью всего проекта» + «запусти пустого агента-ревьювера»

   Основная сессия ревьюит по рискам: деньги, идемпотентность, гонки. Второй агент получает
   только репозиторий и ТЗ, без нашей истории, чтобы не повторять выводы первой сессии. Код
   параллельно вычитывал сам по слоям: domain → services → api.

## Где модель ошиблась
- Предложила `extra="forbid"` и для вебхука. Это сломало бы приём новых полей от банка, поэтому
  при внедрении оставили его только для `POST /payments`.
- Второй, независимый проход ревью нашёл то, что пропустила основная сессия:
  - `kvıtto10` (турецкая «ı») принимался как `KVITTO10`;
  - 422-тесты проверяли только код ответа;
  - строки от прерванного прогона роняли тесты.

  Всё исправлено и закрыто тестами.

## Что заметил сам
- Модель вела ветки цепочкой, а не по схеме «задача → мёрж в main → новая ветка». Заметил при
  разборе структуры веток. Собрал всё в один PR и закрепил правило в CLAUDE.md.
- На предложение `extra="forbid"` проверил, не расходится ли это с ТЗ. Ответ остаётся
  стандартным 422 FastAPI, а значит, это более строгая, но допустимая трактовка.
