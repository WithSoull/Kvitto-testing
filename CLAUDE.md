# CLAUDE.md — правила для агентов

Сервис платежей Квитто. FastAPI + PostgreSQL. Пиши простой и понятный код ровно под
поставленную задачу.

Прежде чем начать задачу, прочитай:
- [docs/SPEC.md](docs/SPEC.md) — что делаем (источник истины по поведению API);
- [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — как делаем: слои, модель данных, потоки, план;
- [docs/DECISIONS.md](docs/DECISIONS.md) — принятые решения и их причины.

Если требования неясны или задача противоречит SPEC / ARCHITECTURE — остановись и спроси автора
(или агента, который поставил тебе задачу), а не додумывай и не «улучшай» молча.

## Стек
Python 3.12 · FastAPI · Pydantic v2 · SQLAlchemy 2.0 **async** + asyncpg · PostgreSQL 16 · Alembic ·
uv · pytest + pytest-asyncio + httpx · ruff · mypy --strict · Docker Compose.

## Команды
```bash
uv sync                                   # зависимости
docker compose up -d db                   # Postgres (БД kvitto и kvitto_test)
uv run alembic upgrade head               # миграции
uv run uvicorn app.main:app --reload      # dev-сервер
uv run pytest                             # тесты (нужен поднятый db)
uv run ruff check . && uv run ruff format --check .
uv run mypy .
docker compose up --build                 # всё целиком
```
Зависимости добавляй только через `uv add` / `uv add --dev`, руками `pyproject.toml` не правь.

## Архитектура (кратко, подробно — ARCHITECTURE.md)
- `app/api/` — роутеры, только HTTP: принять запрос, вызвать сервис, вернуть `response_model`.
  Без бизнес-логики и без SQL.
- `app/services/` — use-case'ы: транзакция, запросы через ORM, вызовы domain. Ничего не знает про
  HTTP (`HTTPException`, `Request`, коды ответов запрещены).
- `app/domain/` — чистые функции и доменные исключения. **Никаких импортов** SQLAlchemy, FastAPI, I/O.
- `app/db/` — модели и сессия.
- Доменные исключения маппятся в HTTP **только** в `app/api/errors.py`.
- Не добавляй слои и абстракции (репозитории, базовые CRUD-классы, DI-контейнеры, фабрики),
  которых нет в ARCHITECTURE.md.

## Деньги — жёсткие правила
- Деньги — только `int` в копейках. `float`, `Decimal` и `round()` для денег **запрещены**.
- Проценты — целые числа, деление — только `//` и `divmod`.
- В БД деньги хранятся в `BIGINT`.
- Любое изменение в `domain/money.py` или `domain/promo.py` сопровождается табличными тестами.
- Инвариант `amount == price - discount` и `sum(schedule) == amount` никогда не нарушается.

## Async и БД
- Все эндпоинты и сервисы `async def`. Внутри — никаких блокирующих вызовов (sync-драйверы,
  `time.sleep`, `requests`).
- `async_sessionmaker(..., expire_on_commit=False)`; одна сессия на запрос через `get_session`.
- Коммит делает сервис в конце use-case'а, а не роутер.
- Никакого lazy loading и `relationship` в ответах — загружай данные явным `select()`.
- Стиль SQLAlchemy 2.0: `Mapped[...]`, `mapped_column`, `select()`. Legacy `session.query()` запрещён.
- Гонки решаются средствами БД: `UNIQUE` + `INSERT ... ON CONFLICT` для идемпотентности,
  `SELECT ... FOR UPDATE` для смены статуса. Не делай «проверить, потом вставить» без защиты.
- Каждое изменение схемы — новая миграция Alembic (`uv run alembic revision --autogenerate -m "..."`),
  которую нужно **прочитать и поправить руками**. Уже существующие миграции не редактируй.
- Enum'ы в БД — `VARCHAR + CHECK`, не нативный `ENUM`.

## API
- Каждый эндпоинт: `response_model`, явный `status_code`, `responses={...}` для ошибок, `tags`,
  `summary`. OpenAPI — часть результата, проверяй `/docs`.
- Схемы запросов/ответов — в `app/schemas/`, отдельные классы для In и Out. ORM-модели наружу не отдавать.
- Форматы ошибок строго по SPEC §5.6. 409 — именно `{"error": "invalid_transition"}`.
- Валидация входа — в Pydantic-схемах (`Literal`, `Field`, `model_validator`), а не в роутере.

## Стиль кода
- Идентификаторы, docstring'и, комментарии, коммиты — **на английском**. Документация в `docs/`,
  README, AI_LOG — **на русском**.
- Полные type hints везде, `mypy --strict` без `# type: ignore` (если без него никак, то с
  кодом ошибки и комментарием, почему).
- ruff (lint + format) — единственный источник истины по стилю; конфиг в `pyproject.toml`.
- Функции короткие, имена говорящие. Комментарий пишем, только если объясняет «почему», а не «что».
- Никаких `print` — модуль `logging`. Никаких голых `except:` / `except Exception: pass`.
- Конфиг — только через `app/config.py` (pydantic-settings), никаких `os.getenv` по коду.
- Не оставляй мёртвый код, закомментированный код и TODO без пояснения.

## Тесты — test-first
- Для `domain/` и для сценариев ТЗ: **сначала падающий тест, потом код**. Покажи, что тест падает.
- Юнит-тесты `tests/unit/` — domain, таблично через `pytest.mark.parametrize`.
- API-тесты `tests/api/` — через `httpx.AsyncClient` против реального Postgres (`kvitto_test`).
  SQLite и моки БД запрещены.
- Тест проверяет **результат**: тело ответа и состояние БД, а не только статус-код
  (например, после 409 перечитать платёж и убедиться, что статус не изменился).
- Каждый тест изолирован транзакцией с откатом (фикстуры в `tests/conftest.py`), порядок тестов не важен.
- Обязательные сценарии ТЗ (SPEC §7) не удалять и не ослаблять.

## Definition of Done (для каждой задачи)
1. `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy .`, `uv run pytest` — всё зелёное.
   Покажи вывод, а не пересказ.
2. Новое поведение покрыто тестами; поведение соответствует SPEC.
3. Если изменилась схема БД — есть миграция, `alembic upgrade head` с нуля проходит.
4. Если принято неочевидное решение или найден подводный камень — добавлена запись в
   `docs/DECISIONS.md` (решение → почему → риск / как в проде).
5. Если меняется поведение API — обновлены SPEC и README (curl-примеры).
6. В конце — короткий отчёт: что сделано, какие решения приняты, что не проверено.

## Git
- Одна задача из плана (ARCHITECTURE §10) — одна ветка от `main`: `feat/...`, `fix/...`,
  `chore/...`, `docs/...`, `ci/...`.
- Conventional Commits на английском: `feat(payments): add idempotency key handling`.
  Коммиты атомарные, каждый проходит тесты.
- PR в `main` с описанием: что, зачем, как проверено. **Мёржит только автор** после ревью.
- Не коммить `.env`, секреты, `__pycache__`, локальные БД. Не делай force-push в `main`.

## Чего не делать
- Не трогать `AI_LOG.md` — это личный лог автора, заполняет он сам (по запросу можно помочь с черновиком).
- Не расширять скоуп: фронтенд, авторизация, реальная интеграция с банком, деплой — вне задачи.
- Не менять принятые решения из DECISIONS без согласования (например, 409 на повтор того же
  статуса — осознанное решение, а не баг).
- Не «чинить» тест, ослабляя проверку, чтобы он прошёл.
