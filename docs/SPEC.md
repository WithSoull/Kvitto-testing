# Спецификация: API платежей Квитто

Источник требований — `ТЗ.pdf`. Этот документ — однозначная трактовка ТЗ; там, где ТЗ молчит
или допускает варианты, решение зафиксировано здесь и продублировано с обоснованием в
[DECISIONS.md](DECISIONS.md).

## 1. Назначение

Сервис, через который онлайн-школа принимает оплату курса: список тарифов, создание платежа
(с промокодом и рассрочкой), просмотр платежа, приём уведомлений банка о смене статуса.

Вне скоупа: фронтенд, авторизация пользователей, реальная интеграция с банком, деплой.

## 2. Глоссарий и инварианты

| Понятие | Правило |
|---|---|
| Деньги | Всегда `int`, в **копейках**. В API, в БД (`BIGINT`), в коде. `float` и `Decimal` для денег запрещены. 19 900 ₽ → `1990000`. |
| `price` | Цена тарифа на момент создания платежа (снапшот хранится в платеже). |
| `discount` | Скидка в копейках, `>= 0`. Без промокода — `0`. |
| `amount` | Сумма к оплате: `amount = price - discount`, `amount > 0`. |
| `schedule` | Список сумм платежей рассрочки в копейках, `sum(schedule) == amount`. Для `card`/`sbp` — `null`. |

## 3. Тарифы

Справочник, создаётся миграцией Alembic (`alembic upgrade head`), изменяемого API нет.

| id | title | price (коп.) |
|---|---|---|
| `basic` | Basic | 990000 |
| `standard` | Standard | 1990000 |
| `premium` | Premium | 2990000 |

## 4. Бизнес-правила

### 4.1 Промокод
- Известные коды: `KVITTO10` → скидка 10% от цены тарифа. Коды хранятся в коде (`domain/promo.py`), процент — целое число.
- Сравнение регистронезависимое, пробелы по краям обрезаются (`" kvitto10 "` == `KVITTO10`).
- Пустая строка / `null` / поле отсутствует → промокода нет.
- Неизвестный код → **422**.
- Округление: `discount = price * percent // 100` (floor, только целочисленная арифметика).

### 4.2 Способ оплаты
- `method ∈ {card, sbp, installment}`.
- `installment` → `installment_months` обязателен, `∈ {3, 6, 12}`, иначе **422**.
- `card` / `sbp` → `installment_months` должен отсутствовать или быть `null`, иначе **422**.

### 4.3 График рассрочки
```
base, rem = divmod(amount, months)
schedule = [base + 1] * rem + [base] * (months - rem)
```
Лишние копейки идут в первые платежи. Даты не нужны.
Пример: `1990000 / 3` → `[663334, 663333, 663333]`.

### 4.4 Статусы
- Новый платёж — `pending`.
- Разрешённые переходы: `pending → succeeded`, `pending → failed`, `succeeded → refunded`.
- Всё остальное запрещено, **включая переход в тот же статус** (`succeeded → succeeded` → 409).
  Это буквальное следование ТЗ; минусы описаны в DECISIONS.
- Конечные статусы: `failed`, `refunded`.

## 5. API

OpenAPI 3.1 генерируется FastAPI (`/openapi.json`, `/docs`). Все эндпоинты описаны через
`response_model`, задокументированы коды ответов и заголовки.

### Модель Payment (ответ)
```json
{
  "id": "6f1c2a0e-...-uuid",
  "status": "pending",
  "tariff_id": "standard",
  "amount": 1791000,
  "discount": 199000,
  "method": "installment",
  "installment_months": 3,
  "schedule": [597000, 597000, 597000],
  "email": "user@example.com",
  "created_at": "2026-10-15T12:00:00Z"
}
```
Ровно эти поля, служебные (`idempotency_key`, `request_hash`, `price`, `promo_code`) наружу не отдаются.
`created_at` — ISO 8601 с таймзоной (UTC).

### 5.1 `GET /tariffs`
- **200** — `[{ "id": "basic", "title": "Basic", "price": 990000 }, ...]`, сортировка по цене.

### 5.2 `POST /payments`
Тело:
| поле | тип | обяз. |
|---|---|---|
| `tariff_id` | string | да |
| `email` | email | да (обрезаем пробелы, приводим к нижнему регистру) |
| `method` | `card` \| `sbp` \| `installment` | да |
| `installment_months` | `3` \| `6` \| `12` \| null | только для `installment` |
| `promo_code` | string \| null | нет |

Заголовок `Idempotency-Key` (необязательный, 1–255 символов).

Ответы:
- **201** — платёж создан, тело Payment.
- **200** — передан `Idempotency-Key`, платёж с этим ключом уже есть **и тело запроса совпадает** → тот же платёж, второй не создаётся.
- **422** — тот же `Idempotency-Key`, но **другое тело запроса** (`type: "idempotency_key_reused"`).
- **422** — ошибки валидации, неизвестный промокод (`unknown_promo_code`), неизвестный тариф (`unknown_tariff`).

«Совпадение тела» — сравнение SHA-256 от канонического JSON нормализованного запроса
(после валидации Pydantic: промокод в верхнем регистре, email в нижнем, ключи отсортированы).

Ключ идемпотентности глобальный (мерчантов/авторизации нет), без TTL.

### 5.3 `GET /payments/{id}`
- **200** — Payment.
- **404** — `{"detail": "Payment not found"}`.
- **422** — `id` не UUID.

### 5.4 `POST /webhooks/bank`
Тело: `{ "payment_id": "<uuid>", "status": "succeeded" }`. `status` — одно из четырёх значений.

Порядок проверок:
1. *(бонус 1, реализован)* Подпись: заголовок `X-Signature` = hex(HMAC-SHA256(raw_body, WEBHOOK_SECRET)). Нет/неверная → **401** `{"detail": "Invalid signature"}`.
   Исключение: тело, которое вообще не является JSON, FastAPI отклоняет с 422 ещё до проверки подписи (см. DECISIONS).
2. Валидация тела → **422**.
3. Платежа нет → **404** `{"detail": "Payment not found"}`.
4. Переход запрещён → **409** `{"error": "invalid_transition"}`; статус не меняется.
5. Успех → **200** `{"result": "ok"}`.

### 5.5 `GET /payments` *(бонус 2, реализован)*
Query: `email` (точное совпадение без учёта регистра), `status`, `limit` (1–100, по умолчанию 50), `offset` (>= 0).
- **200** — список Payment, сортировка `created_at DESC, id DESC`.
- **422** — `limit`/`offset` вне диапазона, неизвестный `status`.

### 5.6 Формат ошибок
- Ошибки валидации — стандартный ответ FastAPI 422.
- Бизнесовые 422 (промокод, тариф, ключ идемпотентности) — **в том же формате**, что и FastAPI:
  `{"detail": [{"loc": ["body", "promo_code"], "msg": "Unknown promo code", "type": "unknown_promo_code"}]}`.
- 404 / 401 — `{"detail": "..."}`.
- 409 — строго `{"error": "invalid_transition"}` (как в ТЗ, без обёртки `detail`).

## 6. Нефункциональные требования
- Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 async + asyncpg, PostgreSQL 16, Alembic.
- Запуск одной командой: `docker compose up` (миграции применяются при старте контейнера).
- Конфигурация через переменные окружения (`DATABASE_URL`, `WEBHOOK_SECRET`), пример — `.env.example`.
- Конкурентная корректность: параллельные запросы с одним `Idempotency-Key` не создают дублей
  (уникальный индекс + `INSERT ... ON CONFLICT`); параллельные вебхуки не нарушают машину
  состояний (`SELECT ... FOR UPDATE`).

## 7. Тесты (минимум из ТЗ + наши)
Обязательные сценарии ТЗ (проверяют **тело ответа и состояние БД**, а не только код):
1. Сумма с промокодом и без, промокод в нижнем регистре.
2. Сумма графика == сумме к оплате для 3, 6, 12 месяцев.
3. Повтор с тем же `Idempotency-Key` не создаёт второй платёж.
4. Запрещённый переход → 409, статус не изменился.
5. Несуществующий платёж → 404.

Дополнительно: юниты на domain (график, скидка, переходы — таблично), неизвестный промокод,
валидация `installment_months`, повтор ключа с другим телом, повторный вебхук того же статуса,
подпись (валидная / неверная / отсутствует), фильтры списка.
